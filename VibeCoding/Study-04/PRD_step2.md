# PRD Step 2: 재료 기반 레시피 추천

<!-- Created: 2026-09-11 19:47:57 +09:00 -->

## 1. 개요

Step 1에서 인식하고 사용자가 확인한 재료 목록을 입력으로 받아, OpenRouter의 `inclusionai/ling-3.0-flash-vl:free` 모델로 만들 수 있는 레시피를 생성한다. 사용 가능한 재료를 우선 사용하고 부족한 재료는 별도로 구분한다.

## 2. 목표

- 사용자가 가진 재료로 실행 가능한 레시피를 추천한다.
- 조리 시간, 난이도, 인분, 부족한 재료를 함께 제공한다.
- 재료가 실제로 사용되는지 확인 가능한 단계별 조리법을 반환한다.
- Step 3에서 저장할 수 있도록 안정적인 레시피 JSON을 제공한다.

### 범위 제외

- 의료 목적의 식단 처방
- 알레르기 안전성의 자동 보장
- 재료 가격 및 매장 재고 조회
- 레시피 사진 생성

## 3. 입력

```json
{
  "ingredients": [
    { "name": "달걀", "quantity": "6개", "condition": "신선해 보임" },
    { "name": "대파", "quantity": "1대", "condition": "양호" }
  ],
  "preferences": {
    "servings": 2,
    "maxMinutes": 30,
    "difficulty": "easy",
    "diet": "none",
    "avoid": []
  }
}
```

사용자가 Step 1 결과를 수정했다면 수정된 값만 전송한다. `preferences`는 선택 사항이며, 서버에서 허용된 값만 통과시킨다.

## 4. 주요 사용자 흐름

1. 사용자가 Step 1에서 재료 목록을 확정한다.
2. 인분, 조리 시간, 난이도, 식단 선호를 선택한다.
3. 사용자가 `레시피 추천`을 실행한다.
4. 서버가 정규화된 재료와 선호 조건을 모델에 전달한다.
5. 추천 레시피 목록과 부족한 재료를 표시한다.
6. 사용자가 레시피 상세를 열고 저장하거나 다시 생성한다.

## 5. 기능 요구사항

- 기본 추천 수는 3개, 최대 5개로 제한한다.
- 각 레시피는 핵심 재료와 선택 재료를 구분한다.
- 보유 재료 사용률을 계산해 표시한다.
- 부족한 재료는 `requiredMissing` 배열로 별도 제공한다.
- 조리 단계는 번호가 있는 순서 목록이어야 한다.
- 모델이 불확실한 식재료를 근거로 위험한 조리법을 제시하지 않도록 한다.
- 날것 섭취, 알레르기, 임산부 등 안전 관련 주의가 필요한 경우 명확한 주의 문구를 포함한다.
- 모델 응답이 스키마와 다르면 서버가 한 번 재시도하고, 실패하면 오류를 반환한다.

## 6. 결과 데이터 계약

```json
{
  "recipes": [
    {
      "title": "대파 달걀 볶음",
      "summary": "간단하게 만들 수 있는 2인분 반찬",
      "servings": 2,
      "timeMinutes": 15,
      "difficulty": "easy",
      "usedIngredients": ["달걀", "대파"],
      "requiredMissing": ["식용유", "소금"],
      "ingredients": [
        { "name": "달걀", "amount": "3개" },
        { "name": "대파", "amount": "1/2대" }
      ],
      "steps": [
        "대파를 송송 썬다.",
        "팬에 기름을 두르고 대파를 볶는다.",
        "풀어 둔 달걀을 넣고 익을 때까지 저어 준다."
      ],
      "tips": ["불을 중약불로 유지하면 달걀이 부드럽습니다."],
      "safetyNotes": []
    }
  ]
}
```

## 7. API 설계

### `POST /api/recipes/recommend`

- 요청: JSON, Step 1의 확정 재료와 사용자 선호
- 모델: `inclusionai/ling-3.0-flash-vl:free`
- 성공: `200 OK`, 레시피 결과 데이터 반환
- 입력 오류: `400 Bad Request`
- 재료가 부족함: 성공 응답 안에 `requiredMissing`으로 표시
- 모델 또는 제공자 오류: `502` 또는 `503`

프롬프트에는 “재료 목록에 없는 재료를 보유 재료처럼 표현하지 말 것”, “알 수 없는 양은 추정임을 표시할 것”, “JSON만 출력할 것”을 포함한다. 서버는 모델 출력을 HTML로 렌더링하지 않고 구조화된 필드로만 화면에 표시한다.

## 8. 화면 요구사항

- 조건 입력: 인분 스테퍼, 최대 조리 시간, 난이도 선택, 식단 및 제외 재료
- 레시피 목록: 제목, 시간, 난이도, 보유 재료 사용률
- 상세 화면: 재료, 부족한 재료, 조리 단계, 팁, 주의사항
- 액션: 저장, 다시 추천, 재료 목록으로 돌아가기
- 상태: 생성 중, 성공, 빈 추천, 모델 오류

## 9. 안전 및 품질

- 알레르기 정보는 사용자가 직접 입력한 `avoid`를 최우선 조건으로 적용한다.
- “안전함” 또는 “먹어도 됨”을 보장하는 표현을 사용하지 않는다.
- 육류, 달걀, 해산물은 충분히 가열하라는 일반 주의 문구를 상황에 따라 포함한다.
- 레시피 생성 요청을 사용자별로 제한해 비용과 남용을 통제한다.
- 모델 응답 원문은 사용자 화면에 노출하지 않고 필요한 필드만 반환한다.

## 10. 수용 기준

- Step 1에서 확정한 재료만 보유 재료로 사용된다.
- 각 추천에 시간, 난이도, 재료, 조리 단계가 포함된다.
- 부족한 재료가 보유 재료와 섞이지 않는다.
- 선호 조건과 제외 재료가 결과에 반영된다.
- 잘못된 모델 응답이 사용자 화면을 깨뜨리지 않고 오류 상태로 처리된다.
- 결과가 Step 3의 저장 API가 받을 수 있는 레시피 스키마와 일치한다.

## 11. 다음 단계 의존성

Step 3은 이 문서의 레시피 객체를 저장한다. 저장 시 모델 응답 전체가 아니라 검증된 결과 객체와 생성 시점, 사용한 재료 목록을 함께 저장한다.
